  Match All / Match / Rematch

  Works, with one caveat: "items 2–4" is not quite enough.

  Pros:
  - Match All as a mission-level endpoint (GET /api/missions/{id}/matches) is a
    performance win, not just convenience. The engine loads the org's crew,
    their skills and assignment counts in bulk (NFR-2). Doing that once for all
    requirements beats the frontend firing R parallel calls that each redo the
    whole pipeline. Skill scoring per requirement is cheap by comparison.
  - Rematch is genuinely free at the engine level — the ranked list must be
    fully sorted anyway to return the top 3, so "give me the next 3" costs
    nothing extra.

  Cons / gaps in "just request items 2–4":
  - Offset drifts. Between the first call and the rematch, someone may accept a
    mission and drop out of the eligible set. Offset 3 then points at a
    different person, and the candidate who moved from rank 4 to rank 3 is
    silently skipped. An explicit exclude=<crewMemberIds> is the same cost and
    is stable against that.
  - Match results are transient (data-model.md, FR-7). Nothing server-side knows
    who was "previously matched", so the client has to say. That's fine, but it
    has to be in the contract.
  - Match All is not N× the per-requirement call. Two crew members can top-rank
    on two different requirements, so a naive Match All suggests the same person
    twice. Needs a dedupe pass.
  - requiredCount is quantity-based. "Highest ranked candidate for each
    requirement" returns 1, but a requirement may need 4 people.
  - The existing spec already contradicts itself on this: FR-6 says limit
    default 3 max 10, the API table says default 20 max 100. Your "default 3"
    settles it — I'll fix the table.

  Average assignment length instead of 365 days

  The intent is right, the raw number won't work.

  Pros: an org running 3-day sorties cycles crew far faster than one running
  6-month expeditions; a fixed 365-day window over-penalises the first and
  under-penalises the second. Scaling the window to the org's rhythm is the
  correct instinct, and it's one aggregate query per request, not per candidate.

  Cons:
  - A length is not a lookback. If the average mission is 14 days, a 14-day
    window means almost nobody has a "recent" assignment and the penalty goes
    dead. The window wants to be a multiple of average length — "your last ~6
    missions' worth of time" — with the multiplier as a config constant (NFR-6).
  - No data at the start. Before 07, and for any new org, there are no completed
    missions, so there's no average. Needs a configured fallback plus a clamp,
    or one freak 3-year mission blows the window out to nothing meaningful.
  - Determinism (NFR-1) now means "same data, same instant" — the window moves
    as missions close. Already true of a rolling 365 days, but worth stating
    explicitly.
  - Module boundary: matching would read the average from mission.api. Defining
    it over mission durations only (not assignment-weighted) keeps it a single
    indexed aggregate inside one module.

     Context

     docs/features/06-crew-matching.md currently specifies a single
     per-requirement matching endpoint
     and a load penalty measured over a fixed 365-day window. Two things need to
     change before the
     feature is built (no matching, crew or assignment module exists yet — this
     is a spec-only
     change).

     Workflow. A mission lead staffing a mission today would have to call the
     matching endpoint once
     per requirement and reconcile the results by hand. They want Match All —
     one action that drafts
     a candidate for every open seat on the mission — plus Match / Rematch on a
     single requirement,
     returning the next batch of ranked candidates without repeating anyone
     already seen or drafted.

     Load penalty. The 365-day recency window is arbitrary and
     organisation-blind. An org running
     three-day sorties cycles its crew through far more assignments per year
     than one running six-month
     expeditions, so the same window means two different things. The window
     should scale to the
     organisation's own mission tempo.

     - FR-6 says limit is default 3, max 10; the API table says default 20, max 
       100. Contradiction.
     - Match suggestions are transient (FR-7, data-model.md), so nothing
       server-side can know who was
       "previously matched". The exclusion set has to be client-supplied, and
       the contract must say so.

● Good question — it's the crux of the choice, and it changes my answer's
  justification (though not the answer). Let me lay it out.

  No, the frontend doesn't store "all rejected ids" as a separate thing. It
  needs two sets, and it's already holding both because it's rendering them:

  - the draft — who is currently sitting in a seat on any requirement of this
    mission
  - the shortlist — the candidates currently displayed for the requirement being
    rematched

  exclude is the union. The one genuinely new piece of state is that the
  shortlist has to accumulate across rematches, not just hold the latest.
  Without that, rematch 1 shows 4–6, rematch 2 excludes only 4–6 and hands back
  1–3 again — it cycles between two pages. So: Map<requirementId, 
  Set<crewMemberId>>, cleared when the lead fills the seat or leaves. Small,
  short-lived, ~10 lines.

  Why offset loses despite being smaller state (one integer per requirement):

  1. It cannot express the draft. Alice is drafted on requirement 1. Rematching
     requirement 2 with offset=3 returns items 4–6 of requirement 2's ranking,
     which may well include Alice. The server has no idea she's spoken for. So
     the client filters her out locally and now shows 2 of 3 — or offers her
     twice and eats a 409 from A5. You end up needing exclude anyway, and then
     you have two mechanisms whose interaction is ambiguous (does offset count
     positions before or after exclude is applied?). That hybrid is the worst of
     the three.
  2. It drifts silently. Between the two calls another lead offers rank 2 to
     someone; BR-4 now excludes them, rank 4 slides up to 3, and offset=3
     returns old-5,6,7. Old-rank-4 is never shown to anyone and nothing
     indicates it happened.
  3. It's positional, so it can't un-reject. "Actually put Bob back in the pool"
     is a set operation, not a cursor move.

  Offset's simplicity is real but only holds if cross-requirement dedupe isn't a
  requirement — and BR-10 says it is.

  One thing offset would have given for free: knowing when you've run out. I'm
  adding a remainingCount to the per-requirement response to cover that, so the
  Rematch button can disable itself instead of quietly returning a short list.

  The answer on exclude vs. range

  Exclude ids. The frontend does not keep a rejection log — the set it sends is
  the current draft plus the shortlist already on screen, both of which it holds
  anyway to render them. The only genuinely new state is that the shortlist has
  to accumulate across rematches; without that, rematch 1 shows 4–6 and rematch
  2 excludes only 4–6 and hands back 1–3, cycling between two pages. That's a
  Map<requirementId, Set<crewMemberId>> cleared when the seat is filled — small
  and short-lived.

  A position range is smaller state (one integer) but loses on two counts:

  - It cannot say who. Alice drafted on requirement 1 will still surface in
    offset=3 on requirement 2, because the server has no idea the draft exists.
    You add exclude anyway, and then two mechanisms interact ambiguously — does
    the offset count before or after the exclusions? That hybrid is worse than
    either alone.
  - It drifts silently. A candidate becoming ineligible between calls shifts
    everyone below them up one, so the next page skips somebody and nothing
    indicates it.

  Both are recorded in BR-11 so the rejected alternative stays on the record.

  The one thing a range gave for free was knowing when the pool is exhausted, so
  I added FR-14 / remainingCount — eligible candidates neither excluded nor
  returned. Zero disables the Rematch button instead of quietly returning a
  short list.
