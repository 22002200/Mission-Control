     Context

     Mission Control is a walking skeleton today. SecurityConfig carries a
     TODO(auth) and
     permitAll()s every request; the README's "Current limitations" leads with
     "There is no
     authentication"; docs/architecture.md lists Authentication under "Open
     decisions". Feature 01
     seeded two organisations and their users, so there are real accounts — but
     no way to log in as one.

     that turns tenancy

     on it.

     It also lands the first closed domain module (identity). Both existing
     modules are OPEN, so
     ModularityTests has had nothing to bite on. After this change it becomes
     load-bearing.

     Architecture: the one hard problem

     Platform is OPEN infrastructure and must stay free of domain concepts.
     identity will depend on
     platform. So platform must never import identity — that is a cycle, and
     ModularityTests
     would fail the build.

     But the JWT validation path lives in platform, and FR-5 requires rejecting
     any token issued before
     its user's tokensValidFrom — which is identity's data.

     Resolution — a platform-declared SPI that identity implements.

     // platform/TokenValidityPolicy.java  (platform declares, does not 
     implement)
     public interface TokenValidityPolicy {
         boolean isStillValid(UUID userId, Instant issuedAt);
     }

     - Platform's JwtDecoder applies it through an OAuth2TokenValidator<Jwt>,
       injected with
       ObjectProvider<TokenValidityPolicy> and defaulting to "always valid" when
       absent — mirroring the
       existing ObjectProvider<CorsConfigurationSource> + ifAvailable precedent
       in SecurityConfig.
     - identity/internal/UserTokenValidityPolicy implements it by loading the
       user.
     - Dependency direction stays identity → platform only. No cycle.

     Same reasoning for minting: platform owns both the encoder and the decoder,
     so the signing
     secret lives in exactly one place and platform stays domain-free. Identity
     injects a
     platform-published TokenIssuer and supplies claims as plain values (id, org
     id, role name).

     NFR-2, timing safety. AuthServiceImpl.login always runs a BCrypt
     comparison. When no user
     matches, it verifies the supplied password against a fixed dummy hash held
     as a constant, discards
     the result, and throws the same InvalidCredentialsException with the same
     message. Without this,
     an unknown email returns in microseconds and a known one in ~100 ms, which
     is a usable oracle.

     Logout sets tokensValidFrom = now() — the only write on the request path
     besides login
     (NFR-5). Because FR-5 compares against the token's iat, this revokes every
     live token for that
     user, satisfying the acceptance criterion about a second, earlier token.

     NFR-4. No password, hash or token is logged. The Exception catch-all in
     GlobalExceptionHandler logs the exception, so credential exceptions must
     not carry the password —
     they will not.
