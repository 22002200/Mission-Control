● Good questions — let me answer the first and fold the second into the plan.

  Why UserSummary in identity/api

  The spec requires missionLead (id, fullName) on every mission response (FR-4).
  But MissionEntity stores only missionLeadId as a bare UUID with no foreign
  key, because app_user belongs to identity and architecture.md forbids FKs
  across module boundaries. So mission holds an ID and has no way to turn it
  into a name.

  Four reasons it takes this shape:

  - It can't reach into identity.internal. identity is a closed module that
    publishes nothing today. Any reference from mission to UserEntity or
    UserRepository fails ModularityTests with "depends on non-exposed type".
    identity/package-info.java predicts this exact moment: "When feature 04 has 
    to check that a mission lead really is a MISSION_LEAD in the right 
    organisation, that is the moment to add an api package with a lookup 
    interface — not before."
  - The name is only needed for other people's missions. On create the lead is
    the caller, so CurrentUser would do. But a director's list shows missions
    owned by several different leads, and that's the case CurrentUser can't
    answer.
  - It's a Map lookup, not a single get, to satisfy NFR-1. One call per mission
    in a 50-row list is a textbook N+1. Bulk findByIds keeps the list at a
    bounded number of queries.
  - It carries id and fullName and nothing else. No role, no email.
    Architecture's rule is "api should be small — if everything is in api, there
    is no boundary." M2 (mission leads own missions, directors don't) is
    already guaranteed structurally by @PreAuthorize("hasRole('MISSION_LEAD')")
    on create plus setting missionLeadId from the caller, so no role field is
    needed. The organisationId parameter is there to enforce T2 — the lookup
    must never resolve a user from another tenant.

  The alternative was denormalising mission_lead_name onto the mission row.
  Rejected: it's a second source of truth that goes stale the moment a user is
  renamed.

     Feature 04 — Mission Management

     Context

     docs/features/04-mission-management.md is the next spec in the build order
     (01 seed → 02 auth →
     03 skills → 04 missions). Today the backend has three modules — platform,
     shared,
     identity, skill — and the frontend has exactly one authenticated screen.
     There is no mission
     module, no mission table, and no mission UI.

     This feature adds the mission module (Mission, CrewRequirement,
     RequiredSkill), the nine
     endpoints in the spec, and the first real application UI: a mission list, a
     mission detail page,
     and the forms to plan a mission and describe the crew it needs.

     Three things it deliberately does not build: approval transitions (feature
     05), assignments
     (07), and matching (06).

     The one design problem the spec creates

     FR-11, FR-2 and BR-9 all read assignment data, but NFR-3 forbids mission
     from depending on
     assignment — and assignment does not exist yet. Resolution, agreed with the
     user:

     mission declares a consumer-side port in mission.api, and ships a no-op
     adapter now.
     Feature 07 supplies the real one. The port must live in mission.api, not
     assignment.api,
     otherwise mission → assignment is exactly the cycle ModularityTests exists
     to catch.

     Consequences to accept and document:

     - acceptedCount is 0 and fullyStaffed is false for any mission with
       requirements.
     - Crew members get an empty mission list — which is correct, they have no
       assignments.
     - POST /start always 409s in the running app. This is moot in practice: a
       mission cannot reach
       APPROVED at all until feature 05 ships. The fully-staffed success path is
       proved in unit and
       slice tests (which mock the port) rather than end to end. See Testing.
