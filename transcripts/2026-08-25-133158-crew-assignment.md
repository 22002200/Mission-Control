     Why mission.api grows

     assignment needs three things from mission it cannot get today, and each
     has a different
     access contract, which is why they do not collapse into one method:

     1. A permission-aware locked read for lead/director commands (offer,
        withdraw).
        MissionPlans already owns that policy — reuse it rather than restate it.
     2. A permission-free read for crew commands (accept, decline). A crew
        member fails
        MissionAccess.requireCanModify by design; their right to act comes from
        the assignment they
        hold, which is assignment's own rule (BR-6), not mission's.
     3. A bulk window lookup for rendering GET /api/assignments/me and for both
        read models.

     Endpoint flows

     POST /api/missions/{missionId}/assignments —
     @PreAuthorize("hasRole('MISSION_LEAD')") so a
     crew member never reaches a mission lookup and cannot learn a mission
     exists.

     1. missionPlans.forStaffingUpdate(missionId) — locks the mission row first
        (the ordering
        MissionLoader insists on), applies visibility (404) and
        owner-or-director (403).
     2. BR-9: refuse a director with 403 — they can see the mission, so 403 is
        the honest answer.
     3. BR-1: status == APPROVED or 409 invalid-transition.
     4. Requirement is on this mission (404 if not — MissionPlan.requirement
        already exists).
     5. BR-10: crewMemberIdOf/userIdsByCrewMemberId resolves the crew member
        inside the caller's
        organisation, or 404.
     6. BR-2: OFFERED + ACCEPTED for the requirement < requiredCount, or 409
        requirement-full.
        Safe under concurrency because step 1 holds the mission row.
     7. Insert OFFERED. A5 is a partial unique index; a violation maps to 409
        duplicate-assignment.

     GET /api/missions/{missionId}/assignments — missionPlans.forStaffing for
     the 404/403 gate,
     then three queries total: the assignments, userIdsByCrewMemberId,
     UserDirectory.findByIds.
     Grouped by requirement, requirements taken from the plan so an unfilled
     line still appears (NFR-4).

     GET /api/assignments/me — @PreAuthorize("hasRole('CREW_MEMBER')"). One
     paged query filtered
     by status, then MissionWindows.findByIds and findRequirements for the page.
     timeframe is
     resolved against the mission window and the injected Clock, and the spec
     gains the definition it
     is missing: CURRENT = startsAt <= now <= endsAt, UPCOMING = startsAt > now,
     PAST =
     endsAt < now. Mission dates, not mission status, so a mission nobody
     remembered to close still
     reads as past.

     POST /api/assignments/{id}/accept — the interesting one.

     1. Load the assignment, tenant-scoped; 404 otherwise.
     2. BR-6: caller's crewMemberIdOf equals the assignment's, or 403.
     3. MissionWindows.lockForUpdate(missionId, org) — the mission lock is 
        always taken first,
        which is what keeps this deadlock-free against close.
     4. AssignmentRepository.lockNonTerminalFor(crewMemberId) —
        ... where crew_member_id = ? and status in (1,2) order by id for update.
        This is the NFR-3
        serialisation point: two overlapping acceptances by the same person lock
        the same row set in
        the same order, so one blocks rather than both proceeding. The mission
        lock alone cannot do
        this — the two acceptances are on different missions.
     5. BR-7: status is OFFERED, or 409 invalid-transition.
     6. BR-2 re-checked (a seat may have filled since the offer), or 409
        requirement-full.
     7. BR-3/BR-4: the crew member's other ACCEPTED assignments →
        MissionWindows.findByIds → any
        not-CLOSED window overlapping this one is 409 schedule-conflict,
        carrying the conflicting
        mission's name and dates as problem properties, the way
        MissionUnderstaffedException carries
        its shortfalls.
     8. ACCEPTED, respondedAt = now. Steps 3–8 are one transaction (NFR-1).

     decline / withdraw — same load-and-authorise shape; both take the mission
     row lock so they
     serialise against close and against a concurrent accept; both are pure
     transitions under BR-7.
     Withdraw is owner-lead-or-director via forStaffingUpdate; decline is the
     named crew member.

     MissionClosedListener — one update assignment set status = WITHDRAWN, 
     responded_at = ? where mission_id = ? and status = OFFERED. ACCEPTED rows
     untouched (BR-8): they are the crew
     member's history. Runs inside the closing transaction, after the mission
     row is already locked.

  What was built

  Backend — the assignment module
  (backend/src/main/java/com/missioncontrol/assignment/): entity, pinned-code
  enum, repository, service, two controllers, an event listener, and
  implementations of both consumer-side ports (StaffingReadModel,
  CrewLoadReadModel). ModularityTests picks it up with no edit and passes, so
  the boundaries hold.

  Three things needed care:

  - Closing a mission withdraws its offers via a new
    mission.api.MissionClosedEvent with a plain @EventListener — synchronous,
    inside the closing transaction, so the two commit together. A read model
    can't carry a write, and a method call would have been the cycle.
  - mission.api grew a second view. MissionPlans reads the caller and answers
    403/404, which is right for a lead offering a place; a crew member accepting
    one fails that check by design. So MissionWindows sits beside it:
    org-scoped, no permission check, plus the row lock. MissionStatus moved to
    api because /assignments/me renders it.
  - Two locks, always mission-first. The mission row serialises two people
    racing for the last seat; it cannot serialise one person accepting two
    overlapping missions, so acceptance also locks that crew member's own open
    rows, ordered by id. AssignmentConcurrencyIT proves both races and the
    close-vs-accept one, 4 repetitions each.

  Frontend: Offer on the matching board (where the reasoning for choosing
  someone is visible), Withdraw on the mission page under each requirement, and
  Your assignments above the crew member's board with the FR-9 filters scoped
  inside the section.
